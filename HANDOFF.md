> **Current story (2026-07-15) — Epic ONB / ONB4 SHIPPED: the ONE-TIME KEY CLAIM. The onboarding CORE (ONB1–ONB4) is complete. STOPPED for the independent ONB4 audit.**
> The last piece of the inverted token lifecycle: an approved agent finally gets a credential — minted only after a human approves, claimed exactly once by the party that will use it, never through an operator's clipboard or a log.
> **The claim secret is minted at JOIN, hash-only.** A `mcc_` secret (256-bit, `backend/src/services/claim.ts`) is generated when the agent submits its join request, stored as a **sha256 hash** with a TTL clamped to **≤ the invite's expiry**, and returned to the agent **exactly once** in the join response. Only the hash is in the DB (the `arturita_bindings` pattern). New nullable columns on `agent_join_requests`: `claim_secret_hash`, `claim_secret_expires_at`, `claimed_at` (idempotent ALTERs + fresh CREATE; nothing backfilled — a pre-ONB4 row has a null hash and simply cannot be claimed).
> **The claim is fail-closed with NO oracle.** Public `POST /api/agent-join-requests/:id/claim-api-key` `{claimSecret}`. **Every failure is one identical flat 404** — unknown request · not approved · **missing agent row** · wrong secret · expired · already claimed · lost race. This is a **deliberate deviation from design §3.6** (which specified distinct 403/409/410) to match the epic's no-oracle posture — **flagged for the auditor** below. The secret is matched with a **constant-time compare** (`hashesEqual`/`timingSafeEqual`, the `arturita_bindings` helper), never a SQL `=` or Node `===`.
> **Agent-must-exist honoured (ONB3 auditor #3).** The claim re-reads the agent row and fails closed if it is absent or already credentialed — it never mints against `status='approved'` alone, which also neutralises M-1's ghost-agent shape (an "approved" request whose agent insert failed cannot be claimed against).
> **Single-use = two atomic CAS.** The claim consume is one conditional UPDATE (`claimed_at IS NULL` is the compare-and-set; `claimed_at` set + secret hash **cleared** in the same statement); the `mca_` token is then minted under a **second CAS** (`api_token_hash IS NULL`) and stored **hash-only** on the agent. `services/claim.ts` owns both statements — like `invite-consume.ts`, neither may be re-implemented at a route. A **concurrency test** drives two simultaneous claims and asserts exactly one 200 + one token hash.
> **The raw token appears once, to the claimer, nowhere else.** Never persisted plaintext, never logged (`mcc_`/`mca_` redacted by `log-redaction.ts` — which already reserved `mcc_`), never in an operator UI (`operatorCanSeeClaimedKey` literal `false`). The claimed agent stays `low_trust_review` (A2 gate still applies); `claude_code` stays plan-mode.
> **Posture + guard honest.** `TOKEN_CLAIM_IMPLEMENTED` flips **true**; the landmine guard (`auth-scoping.test.ts`) now asserts the claim route exists **iff** the constant, **both directions**. Exposure follows the deployment profile exactly like the join — hosted prod answers a flat 404 without `MC_ENABLE_REMOTE_ONBOARDING`. `perIpRateLimit()` wired onto the claim (the fixed socket/`Fly-Client-IP` keying, ONB3 M-2). The join response now carries the `mcc_` secret, so ONB3 tests that asserted "no secret in the join response" were updated to ONB4 reality.
> **Where to look:** `backend/src/services/claim.ts` (the two CAS statements + the fail-closed chain), `backend/src/routes/agent-invites.ts` (the join mints the secret; the new claim route), `backend/src/tests/onb4-claim.test.ts` (12 driven tests — the fail-closed matrix + concurrency + hash-only + posture gating + redaction).
> **Invariant: 1221 backend tests (+12 ONB4) · 11/11 evals · web build clean.** **Untouched (operator/product calls): the audit/telemetry hooks — still a no-op — and `allowShell`/`MC_ALLOW_SHELL`; the live adapter.**
> **Flags for the ONB4 auditor:** (1) the **flat-404-for-every-failure** decision is a deliberate deviation from design §3.6's distinct codes — verify it is the intended no-oracle posture and that the onboarding doc's failure-state text (now "one flat 404") is honest. (2) M-1's "make it a real transaction" recommendation is **NOT** done — the claim uses two sequential CAS statements with a compensation on the (near-impossible) mint failure, not a DB transaction, because `db.transaction()` opens a second connection the `:memory:` harness cannot follow (per the ONB3 audit); the two-CAS design is single-use-correct without it, but a real transaction remains the end state.
