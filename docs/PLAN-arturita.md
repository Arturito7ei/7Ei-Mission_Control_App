**Epic ONB — Invite-based agent onboarding** (`docs/DESIGN-agent-onboarding.md`): reverse-engineered from the live Paperclip instance (read-only) and mapped to us. Paperclip's onboarding is a **self-describing contract, not a UI**: the operator creates an invite and pastes one ~40-line prompt into *any* agent's chat; the agent then onboards itself — reads a per-invite `onboarding.txt`, picks its own `adapterType`, probes `/api/health` against a server-supplied candidate list, submits a join request describing its own capabilities + runtime config, **waits for a human board approval**, and only then claims its API key, **once**. The design's load-bearing move is the **inverted token lifecycle**: the agent self-describes *first*, a human approves *second*, the credential is minted and claimed *last* — by the party that will use it, never through the operator's clipboard. That is strictly safer than today's model, where `7ei-mc onboard` mints an `mca_` token *before* any human decision and the operator hand-carries it into an `mc.env`. **~70% reuse**: agent identity + hash-only token mint (`middleware/agent-token.ts`), the whole post-onboarding agent API (`routes/agent-api.ts`), external registration + `secureRegistration()` (CC3), the tri-state approvals queue (which already names `agent_create` a gated action), P1 low-trust containment, `web/lib/adapterProfile.ts`, and the `arturita_bindings` hash+TTL+single-use precedent. **Four net-new objects**: the invite, the join request, the one-time claim, and a **server-side adapter registry** (today `runtime` is a free-text column and per-runtime config lives client-side only — the gap doc ranks this #4). Plus one generated document and one dialog. The invite gate **stacks in front of** A2/P1 and softens nothing — an invite-onboarded agent lands in `low_trust_review` regardless of runtime, so it is *more* contained than one created by the Add-Agent wizard today. The one posture question the operator must answer: a **public join endpoint on a hosted backend** (Paperclip's is loopback-only) — recommended yes, behind the approval gate + single-use default + short TTL + the (already-written, currently uncalled) per-IP rate limit, since a leaked invite then buys an attacker a row in a human's inbox rather than a credential. MVP = ONB1–ONB4 + ONB6; ONB5 only matters for gateway/webhook runtimes. **STATUS (2026-07-15): ✅ EPIC ONB COMPLETE.** All MVP stories shipped and independently audited — **ONB1–ONB4** (the security core), **ONB6** (the create-invite UI + copy-able prompt + agent-side CLI), the **audit-trail enablement** (audit H-1), and **ONB7** (docs / go-live: `docs/RUNBOOK-agent-onboarding.md`, the consolidated `GO-LIVE.md`, `docs/SECURITY-posture.md`, master-doc + vault updates). The inverted token lifecycle is real end to end: invite → self-description → **human approval** → one-time claim of the `mca_` credential (minted only after approval, returned once to the claimer, never operator-visible or logged). **ONB5 is explicitly DEFERRED** — it is optional and gateway/webhook-only: the four *available* runtimes (`openclaw_local`, `claude_code`, `cursor`, `openai_generic`) need no server-side reachability check, and ONB5 is a precondition only for marking the still-unbuilt gateway/webhook runtimes `available`. **Operator decisions locked 2026-07-14 (design doc §8 addendum — supersedes §7's Q1–Q4, and ties Epic ONB to Epic H):** the app runs in one of **two deployment profiles chosen by config** — **`hosted`** (multi-tenant, public join gated + hardened) and **`packaged`/local** (single-tenant, loopback-trusted, Paperclip-style; the future `.dmg`) — and **the onboarding posture is derived from the profile, never hardcoded**. All system settings become one **declarative, versioned config bundle** that the Export/Import portability moves between machines and that **Epic H's H4 installer seeds a fresh machine from** — so ONB and H are designed together rather than growing two config formats. **Secrets always stay in the encrypted store, never in the bundle or the package.** Four posture defaults are baked in as **invariants, not switches**: (1) public join endpoint **OFF by default**, gated by profile — packaged = loopback-trusted, hosted = requires an explicit remote-onboarding enable **plus** full hardening; (2) invites are **SINGLE-USE by default** (multi-use is an explicit, bounded opt-in — we invert Paperclip's default); (3) **every invite-created agent lands in `low_trust_review` regardless of runtime** (extends CC3 beyond `claude_code`); (4) the **raw claimed token is never shown in the UI or the clipboard** — only the claiming agent reads it, once, from the raw HTTP response.

**Epic H — Packaging & Distribution** (`docs/DESIGN-packaging.md`): a replicable, **installable** product — a signed, notarized macOS `.dmg` that stands up a full local **`packaged`/loopback** instance on someone else's Mac (Fastify backend on a **local libSQL file** · the Next.js UI · opt-in host daemons: Ollama, the Whisper bridge, the OpenClaw/Claude-Code adapters), plus an iPhone remote surface. **~70% reuse** — the heavy foundations were built anticipating this exact installer: the two-profile abstraction (`deployment-profile.ts`), the secret-free versioned **config bundle** (`config-bundle.ts` + `assertNoSecrets()`), the portability slices (`portability.ts`), the AES-256-GCM secret store, the launchd-supervised **zero-dep** adapters, and a DB layer that **already speaks `file:`** (`db/client.ts`, so Turso is optional). **Recommended bundling approach: an Electron shell supervising bundled sidecar services** (stack-fit — its bundled Node runs the backend as a child with one signature chain; Chromium parity = zero Next.js UI risk; `electron-builder` automates the sign/notarize gauntlet), with **Tauri v2 the documented runner-up**. The **one load-bearing net-new piece is loopback identity (H6)** — Clerk is cloud/multi-tenant and can't authenticate a single-tenant loopback instance; everything else is wiring existing pieces into a supervised, signed bundle. **Secrets are generated per-install into the macOS Keychain, never baked into the image** (`SECRETS_ENC_KEY`/`RUN_TOKEN_SECRET`), and boot **fails closed on the dev-default key** (the GO-LIVE §1 follow-up ships here).
